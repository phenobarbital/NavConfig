Overview

NavConfig is the default configuration layer of the Navigator Framework, and works equally well as a stand-alone tool for any Python application. It loads configuration directives from several sources and combines them into one immutable object shared across modules:

  • Environment files (.env)
  • INI files, through configparser
  • TOML and YAML files
  • pyproject.toml
  • Redis
  • HashiCorp Vault
  • Python settings modules (settings/settings.py)

Secrets live in .env files or in Vault; structured settings live in INI/TOML/YAML files. The separation keeps credentials out of the files you commit, and lets configuration vary per environment without touching application code.

Installation

pip install navconfig

Optional backends are exposed as extras:

pip install navconfig[redis]      # Redis reader
pip install navconfig[hvac]      # HashiCorp Vault
pip install navconfig[logstash]  # Logstash logging handler
pip install navconfig[all]       # everything

The kardex CLI

NavConfig ships a command line tool called kardex that bootstraps and maintains the configuration layout of a project. It is organised in command groups, each with its own actions.

CommandWhat it does
kardex env createCreate the default project structure.
kardex env create --splitSame, plus the supplementary .env.* files.
kardex env new <name>Add an environment from the shared env/.env.
kardex vault createWrite the HashiCorp Vault directives into env/<env>/.env.
kardex vault migratePush the variables of an environment into Vault.
kardex vault save VAR:VALUEStore one or more variables in Vault.
kardex log enableEnable the [logging] section of etc/config.ini.

Every group accepts --path to point at a project root other than the current directory, and kardex <group> <action> --help lists the full set of options.

Bootstrap a project

kardex env create --env dev

This generates the following structure in the current directory:

.
|-- env/
|   |-- .env          shared across environments, no ENV= pin
|   +-- dev/
|       +-- .env      pinned to ENV=dev
|-- etc/
|   +-- config.ini
|-- logs/
+-- templates/
  • env/.env — values shared by every environment; kardex env new uses it as the template for new ones.
  • env/dev/.env — environment variables: secrets, feature flags, paths.
  • etc/config.ini — INI settings consumed by NavConfig, including the [logging] section.
  • logs/ — where rotating log files are written.
  • templates/ — default directory for template files.

Existing files are never overwritten. Pass --force when you do want them replaced, and --path to build the structure elsewhere:

kardex env create --env dev --path /srv/myapp

Split configuration across several files

NavConfig loads .env first and then a set of supplementary files, which keeps unrelated concerns apart. Pass --split to create them all:

kardex env create --env dev --split
env/dev/
|-- .env             base configuration and Vault credentials
|-- .env.resources   paths and resource-level directives
|-- .env.databases   database connection settings
|-- .env.api         HTTP layer settings
|-- .env.cache       Redis / cache backend settings
+-- .env.local       local overrides, loaded last (keep out of git)

Files are loaded in that order, so .env.local always wins. Everything ends up in the same flat namespace, so config.get("DBHOST") works regardless of which file declared it.

Environments

Add as many environments as the project needs:

kardex env new prod
kardex env new staging --split

Each command copies env/.env (or the bundled sample if no shared file exists) into env/<name>/.env, adjusting the ENV variable automatically. Select one at runtime through the ENV variable:

ENV=prod python app.py

NavConfig then loads env/prod/.env and any INI file referenced by its CONFIG_FILE directive.

HashiCorp Vault

Configure the connection

kardex vault create --env dev \
    --url http://vault.internal:8200 \
    --token "$VAULT_TOKEN" \
    --mount-point myapp

This appends a delimited block to env/dev/.env — creating the file if it does not exist yet — with the directives NavConfig actually reads:

VAULT_ENABLED=true
VAULT_URL=http://vault.internal:8200
VAULT_TOKEN=...
VAULT_MOUNT_POINT=myapp
VAULT_VERSION=2
# VAULT_ENV=

Secrets are read from <VAULT_MOUNT_POINT>/<ENV>/ and merged on top of the file-based values. Set VAULT_ENV to read from a path segment other than ENV; set NAVCONFIG_FILE_OVERRIDE_ENABLED=true to let the .env files win over Vault instead.

Re-running the command updates only the directives you pass on the command line, which makes token rotation a one-liner. Pass --force to rewrite the whole block.

Migrate an existing .env into Vault

kardex vault migrate --env dev --dry-run   # inspect first
kardex vault migrate --env dev

Two families of variables are deliberately left in the .env file, because NavConfig needs them before it can reach Vault:

  • the Vault directives themselves (VAULT_*), and
  • the bootstrap directives (ENV, CONFIG_FILE, SITE_ROOT, …), which can be included anyway with --include-bootstrap.

Useful options: --include-extra (also migrate the .env.* files), --keep-existing (never overwrite a key already stored in Vault), --file (migrate an arbitrary file) and --yes (skip the confirmation prompt). Values are masked in the output, and nothing is written until you confirm.

Store single variables

kardex vault save DB_PASSWORD:s3cr3t
kardex vault save "DSN:postgres://user:pass@host:5432/db" API_KEY:abc123

Only the first colon separates the name from the value, so values may contain colons themselves.

Logging

kardex log enable

That writes the [logging] section of etc/config.ini — creating the file from the bundled sample when missing — with console and rotating-file output enabled, and creates the log directory. Comments in the INI file are preserved.

To also forward records to a Logstash server:

kardex log enable --logstash \
    --logstash-host logs.internal \
    --logstash-port 5044 \
    --logstash-level INFO

Note. The Logstash handler needs pip install navconfig[logstash]. NavConfig warns and falls back to the remaining handlers when the dependency or the server is unavailable.

Other options: --loglevel, --logdir, --quiet (no console output), --no-file (no rotating file handler) and --mailer (email alerts on CRITICAL records).

Apply the resulting configuration in your application:

import logging
from logging.config import dictConfig
from navconfig.logging import logging_config

dictConfig(logging_config)

logger = logging.getLogger("MY_APP")
logger.info("Hello World")

Reading values

from navconfig import config

APP_NAME = config.get("APP_NAME")   # "MyApp"
APP_NAME = config.APP_NAME          # attribute access also works

Typed accessors

config.get("APP_NAME")                  # str
config.getint("PORT", fallback=8080)    # int
config.getboolean("DEBUG")              # bool
config.getlist("ALLOWED_HOSTS")         # list (comma-separated)
config.getdict("EXTRA")                 # dict

An optional fallback is returned when the key is not found:

config.get("MISSING_KEY", "default_value")

Initialization

NavConfig resolves the project layout and loads the environment the first time one of its package-level names is accessed (config, BASE_DIR, DEBUG, ENV, …), not while the package is being imported. Call navconfig.bootstrap() when you need the environment loaded into os.environ as a side effect without touching any of those names:

import navconfig

navconfig.bootstrap()

Project layout

By default NavConfig looks for files relative to the project root, based on the file type:

File typeDefault location
.envenv/, plus the environment subdirectory
.yml / .tomlenv/
pyproject.tomlproject root
.inietc/

A typical project looks like this:

myapp/
|-- __init__.py
|-- pyproject.toml
|-- env/
|   |-- .env          shared base file
|   |-- dev/
|   |   +-- .env
|   |-- staging/
|   |   +-- .env
|   +-- prod/
|       +-- .env
|-- etc/
|   +-- config.ini
|-- logs/
+-- settings/
    |-- __init__.py
    +-- settings.py   optional

Settings module

Create a Python package called settings in your project to define configuration derived from NavConfig values. Inside settings/settings.py:

import sys
from navconfig import config, DEBUG

LOCAL_DEVELOPMENT = DEBUG is True and sys.argv[0] == "run.py"
SEND_NOTIFICATIONS = config.get("SEND_NOTIFICATIONS", fallback=True)

Variables defined there are accessible through navconfig.conf:

from navconfig.conf import LOCAL_DEVELOPMENT

if LOCAL_DEVELOPMENT:
    print("Running in local development mode.")

Upgrading to 3.0

Breaking changes. NavConfig 3.0 reorganises the CLI into sub-commands and defers initialization; there is no compatibility shim.

2.x3.0
kardex create --env devkardex env create --env dev
kardex new-env prodkardex env new prod
kardex new-env prod --vaultkardex env new prod then kardex vault create --env prod

Two further changes are worth checking before you upgrade:

  • Initialization order. Importing navconfig no longer builds the configuration by itself. Code that relied on import navconfig alone to populate os.environ must call navconfig.bootstrap() explicitly, or read any exported name. This is what makes kardex env create runnable on a project that has no env/ directory yet.
  • Vault directives. The block written by kardex vault create uses VAULT_URL, VAULT_MOUNT_POINT and VAULT_VERSION. The VAULT_ADDR, VAULT_ROLE_ID, VAULT_SECRET_ID, VAULT_SECRET_PATH and VAULT_NAMESPACE variables emitted by new-env --vault in 2.x were never read by the loader.
